## Setup

These steps reproduce the full local development environment from a fresh clone.

### 1. Clone

```bash
git clone https://github.com/<your-org>/datacommons-protocol.git
cd datacommons-protocol
```

### 2. Build contracts

```bash
cd contracts
stellar contract build       # or: soroban contract build
cargo test                   # confirm all contract tests pass
cd ..
```

### 3. Backend

```bash
cd backend
npm install
cp .env.example .env         # fill in DATABASE_URL, contract IDs, IPFS keys, etc.
npm run migrate              # create Postgres tables
npm run dev                  # starts Express on http://localhost:4000
```

### 4. Frontend

```bash
cd frontend
npm install
cp .env.example .env         # fill in VITE_API_URL and contract IDs
npm run dev                  # Vite dev server on http://localhost:5173
```

### 5. Seed example data (optional but recommended)

```bash
# From the repo root, with backend/.env populated and DB migrated:
npx tsx scripts/seed_testnet_data.ts
```

This populates the marketplace with realistic example datasets spanning health, agriculture, and climate research, so you have a non-empty UI to develop against.

### 6. Deploy to Testnet

```bash
DEPLOYER_IDENTITY=<your-stellar-cli-identity> \
BACKEND_ADDRESS=<backend-service-account-public-key> \
bash scripts/deploy_contracts.sh
```

Contract IDs are written to `docs/testnet-deployment.md`. Copy them into `backend/.env` and `frontend/.env`.

## Running tests

```bash
# Contracts (Rust unit + integration tests, Soroban local sandbox)
cd contracts && cargo test

# Backend (Vitest — unit + integration tests, mocked Soroban RPC)
cd backend && npm test

# Frontend (Vitest + @testing-library/react, jsdom)
cd frontend && npm test
```

All three suites must pass before submitting a pull request. The CI workflow (`.github/workflows/ci.yml`) runs them automatically on every push and pull request.

## Making a contribution

1. **Open an issue first** for anything beyond a trivial bug fix or typo. Describe what you want to change and why. This avoids wasted effort on PRs that conflict with existing decisions.
2. **Branch off `main`**: `git checkout -b feature/your-topic`.
3. **Write tests** for every new behaviour. Bug fixes should include a regression test. New features need unit tests and, where practical, an integration or end-to-end test.
4. **Run the full test suite** (`cargo test`, `npm test` in backend, `npm test` in frontend) before pushing.
5. **Keep PRs focused.** One logical change per PR. Separate refactors from feature additions.
6. **PR title** under 70 characters; put context in the description.
7. **Description** should cover: what changed, what was tested, and any known limitations.

## Coding standards

### Rust (contracts)

- Follow `rustfmt` defaults (`cargo fmt`).
- `cargo clippy -- -D warnings` must pass with no warnings before submitting.
- Error variants must be documented in `docs/contract-spec.md`.
- All new contract methods that change state must emit the appropriate provenance event (see `docs/consent-provenance.md`).

### TypeScript (backend & frontend)

- No `any` except in genuinely untyped third-party scenarios; add a `// eslint-disable` comment with a reason.
- All new API routes must have at least one integration test in the corresponding `.test.ts` file.
- Backend route handlers must validate inputs and return descriptive `4xx` errors on bad input.
- Frontend components that call the backend must handle loading, error, and empty states explicitly.

### General

- No hardcoded secrets, addresses, or environment-specific values in source files — use env vars.
- Keep `README.md` accurate. If your change alters a user-visible behaviour described in the README, update README in the same PR. Do not change README's core design decisions — only correct inaccuracies.

## Proposing Phase 2+ features

The README Roadmap lists several deferred features. When proposing one:

1. **Open an issue** tagged with the appropriate phase (`Phase 2`, `Phase 3`, etc.).
2. **Reference the relevant Roadmap item** in your issue. If your proposal doesn't map to an existing Roadmap item, explain why it belongs in the protocol.
3. **Write a short design doc** (a few paragraphs for small things; a proper spec for significant changes) and post it in the issue *before* writing any code. This is especially important for:
   - Contributor split editability (Phase 2: `SplitRegistry`).
   - Reputation and rating systems (Phase 3).
   - Multi-stablecoin and local on/off-ramp support (Phase 4).
   - DAO-style dispute resolution (Phase 5).
   - Federated query execution (Phase 6).

## Phase 1 design decisions that are locked in

The following decisions were made deliberately for Phase 1 and are **not open for re-litigation in PRs targeting `main`**. If you believe one of these decisions is wrong, open a discussion issue — don't submit a PR that silently changes them.

### 1. Fixed-percentage revenue splits, set once at mint

Contributor shares are immutable after `register_dataset` is called. This maps to real research co-authorship agreements (settled before publication), eliminates the governance complexity of editable splits, and makes the provenance trail unambiguous.

The Phase 2 `SplitRegistry` pattern (versioned, owner-governed splits affecting only *future* licenses) is the designed upgrade path. Do not implement editable splits in the Phase 1 contracts.

### 2. Hybrid access control: time-boxed and/or query-metered, per listing

Access terms are set per dataset by the owner at registration. Buyers take the terms as listed; the contract enforces them. This is not a limitation to work around — it is the intended model.

### 3. Stablecoin-only payments (USDC / SEP-41-compliant tokens)

Payments are in a stablecoin. Native XLM is not used for payments. This insulates researchers from local currency volatility. Multi-stablecoin support is Phase 4.

### 4. The backend proxy is the only authorised caller of `consume_query`

The backend's `BACKEND_SIGNING_KEY` is the only key authorised by the contract to call `consume_query`. This is a deliberate MVP centralisation trade-off. Do not add alternative paths from the frontend or from untrusted parties. The Phase 6 federated query execution model is where this changes.

### 5. No raw data on-chain

Dataset bytes are never stored on the Stellar ledger. IPFS/Arweave is the off-chain storage layer. This is a hard architectural constraint, not a configuration option.
